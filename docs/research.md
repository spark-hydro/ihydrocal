# iHydroCal Project Research Report

**Project reviewed:** `ihydrocal.zip` uploaded by the user  
**Inspection location:** `/mnt/data/ihydrocal_inspect/ihydrocal`  
**Report purpose:** Understand the current iHydroCal framework deeply enough to design a `pestpp-swp` workflow for SWAT+ release-water scenario sweeping.

---

## 1. Executive summary

The current iHydroCal project is an early but usable Python framework for SWAT/SWAT+/SWAT+gwflow-oriented calibration, uncertainty analysis, sensitivity analysis, and visualization. The strongest implemented path is currently:

1. create/load a YAML setup file,
2. copy a SWAT+ `TxtInOut` dataset into `ihydrocal_workspace/main`,
3. copy model/PEST++ executables into that workspace,
4. generate `calibration.cal` and `calibration.cal.tpl` from an iHydroCal parameter database,
5. run SWAT+ through `forward_run.py`,
6. extract selected channel streamflow outputs from large SWAT+ output text files,
7. build PEST-compatible simulated-output `.dat` and `.ins` files,
8. create a PEST control file,
9. run `pestpp-glm`, reweight, create `pestpp-ies`, or create/run `pestpp-sen` Morris control files,
10. plot GLM/IES/SEN outputs using analyzer utilities.

The framework already contains a clean conceptual separation between:

- `core/`: configuration, workspace setup, model registry, PEST control-file helpers,
- `models/swatplus_gwflow/`: SWAT+gwflow-specific readers, parameters, outputs, and observation preparation,
- `analyzer/`: model-independent or PEST-specific diagnostic plotting,
- `config/`: default setup YAML, parameter databases, and a PEST forward-run script,
- `examples/`: manually executed scripts and notebooks showing development workflows.

There is **no current `pestpp-swp` implementation**. However, `pestpp-swp` can be added naturally because `core/pest.py` already contains `run_pestpp`, `run_pestpp_ies_workers`, and `run_pestpp_sen_workers`, and the workspace pattern already matches pyEMU/PEST++ worker execution.

The biggest implementation risk is not `pestpp-swp` itself. The bigger design question is **where and how release water should be applied in SWAT+**:

- as a true SWAT+ input-side management/release/point-source operation, or
- as an iHydroCal post-processing scenario layer that adds release flow to selected channels after SWAT+ runs.

For the first implementation, the safer and faster route is the second approach: add a `release_schedule.csv` generated by PEST templates, run the baseline SWAT+ model, extract channel flow, then add release values to the extracted flow table before producing SWP outputs. This keeps the original SWAT+ input model safe and fits the current iHydroCal architecture.

## 3. Package entry points and model registry

### 3.1 `src/ihydrocal/__init__.py`

This file exposes:

```python
from ihydrocal.core import create_model, available_models
__version__ = "0.0.0b3"
from ihydrocal import models
```

The import of `ihydrocal.models` is important because model classes register themselves through decorators when their modules are imported.

### 3.2 `core/base.py`

`BaseModel` is an abstract base class. It provides:

- `model_dir`
- `config`
- `exists()`
- abstract `validate()`
- abstract `read_outputs()`
- a placeholder `run()`

This is a good foundation for multiple hydrologic-model adapters, but most adapters are currently placeholders.

### 3.3 `core/registry.py`

The registry pattern is simple and effective:

- `MODEL_REGISTRY = {}`
- `@register_model("name")`
- `available_models()`
- `create_model(name, model_dir, config=None, **kwargs)`

Currently registered adapters include:

```text
swat
swatplus_gwflow
swat_modflow
apex
apex_modflow
daycent
```

### 3.4 Important naming edge case

The YAML validator allows:

```text
swatplus
swatplus_gwflow
```

but the registry currently has no `swatplus` adapter. It has `swat` and `swatplus_gwflow`. Therefore, a config with `model_type: swatplus` is accepted by `validate_config()`, but `create_model("swatplus", ...)` would fail unless a `swatplus` model adapter is added or aliased.

This matters for `pestpp-swp` because the uploaded default config currently says:

```yaml
project:
  model_type: swatplus
```

while most implemented SWAT+ functionality lives under `models/swatplus_gwflow`.

### 4.6 Critical config/forward-run mismatch

The current `config/forward_run.py` expects:

```python
channel_cfg = cfg["outputs"]["swatplus"]["channel"]
```

and then expects keys like:

```python
channel_cfg["file"]
channel_cfg["variables"]
channel_cfg["cha_ids"]
channel_cfg["id_col"]
```

However, the provided `config/setup_swatplus.yml` does **not** include an `outputs:` section. The example script `examples/scripts/all_workflows.py` also expects `cfg["outputs"]["swatplus"]["channel"]` in `stf_extractor()`.

This is a blocking issue for fully automated runs unless the user’s working config has already been manually extended. For `pestpp-swp`, the plan must add or formalize an `outputs:` section.

Recommended missing block:

```yaml
outputs:
  swatplus:
    channel:
      file: channel_sd_day.txt
      id_col: gis_id
      variables:
        - flo_out
      cha_ids: []
```

For Pecos, `cha_ids` should be populated from `channels_gages.csv` or release-location IDs.

### 5.3 Binary copying

`copy_binaries_to_model()` expects binaries under:

```text

```

For Windows, `get_binary_name()` appends `.exe` when needed.

Current `bin/windows/` contains:


### 5.4 SWP binary gap

There is no `pestpp-swp.exe` in `bin/windows/`, and `config/setup_swatplus.yml` does not include `pestpp-swp` in `binaries.files`.

For `pestpp-swp`, the framework needs either:

- a `pestpp-swp.exe` copied into `bin/windows/`, or
- a user-provided executable available on `PATH`, or
- a config option that uses a full path to `pestpp-swp` instead of copying it.

### 5.5 OS portability edge case

Only `bin/windows/` exists in the uploaded zip. On Linux/macOS, `copy_binaries_to_model()` will look for `bin/linux/` or `bin/macos/` and fail unless those folders are added or binary copying is disabled.

## 6. SWAT+gwflow model adapter and IO

### 6.1 `models/swatplus_gwflow/model.py`

`SWATPlusGwflowModel` is registered as:

```python
@register_model("swatplus_gwflow")
```

Its constructor accepts:

```python
model_dir
output_dir=None
config=None
```

If `output_dir` is not provided, `output_dir = model_dir`. It creates:

```python
self.io = SWATPlusGwflowIO(self.output_dir)
```

This is useful because the user has already asked to avoid fixed `TxtInOut` naming. The model can point to any output directory.

### 6.2 Validation

`validate()` only checks that `model_dir` and `output_dir` exist. It does not yet check for required SWAT+ files such as `time.sim`, `print.prt`, or channel outputs.

For `pestpp-swp`, this is acceptable for first implementation but should later be strengthened.

### 6.3 `models/swatplus_gwflow/io.py`

The IO class reads SWAT+ text files using whitespace-delimited `pandas.read_csv`.

Important implemented readers:

- `read_time_sim()`
- `read_print_prt()`
- `define_sim_period()`
- `read_channel_sd_day()`
- `read_channel_sdmorph_day()`
- `read_channel_sd_mon()`
- `read_channel_sdmorph_mon()`
- `read_basin_wb_mon()`
- `read_basin_wb_yr()`
- `read_gwflow_state_obs_head()`
- `read_channel_flow_day_wide()`
- `read_observed_flow_wide()`
- `read_pcp_file()`
- `read_pcp_files_wide()`
- `read_channel_precip_depth_wide()`

### 6.4 IO edge cases

Important details for future implementation:

1. `read_table()` raises `FileNotFoundError` with the exact file path. Good.
2. Most channel readers use `skiprows=[0, 2]`, while the large-file extractor uses dynamic header detection. These are different assumptions.
3. `define_sim_period()` assumes `time.sim` and `print.prt` can be parsed with `skiprows=1` and contain specific columns.
4. `read_channel_flow_day_wide()` uses `pivot`, which fails if duplicate date/channel combinations exist. The large-output extractor avoids this by keeping long format.
5. `read_observed_flow_wide()` expects long observed data with `Date`, `site_no`, and `Q_cms`, while the PEST observation workflow expects wide `stf_day.obd.csv` with `date, site_...` columns.
6. `read_pcp_file()` expects SWAT+ `.pcp` format with three skipped rows and year/jday/value columns.
7. `read_channel_precip_depth_wide()` assumes `channel_sd_day.txt` reports precipitation as volume in m3 and area in ha, then converts to mm as `precip / area * 0.1`.

### 7.3 Calibration template design

`write_calibration_cal()` writes a SWAT+ `calibration.cal` file from active parameter rows.  
`write_calibration_template()` then converts the value fields to PEST placeholders.

This is calibrated-parameter oriented. Release-water decision variables should **not** be forced into `calibration.cal` unless the releases are truly represented by SWAT+ calibration parameters. For `pestpp-swp`, a separate release template is cleaner.

### 7.4 Parameter-name edge case

`make_pest_parameter_name()` truncates names to 12 characters. This may produce duplicate names if multiple release parameters share the same first 12 characters. For SWP release parameters, a more careful naming scheme is needed, such as:

```text
rel001_jan
rel001_feb
rel447_low
```

or a duplicate-safe function.

## 8. Observation and instruction-file workflow

### 8.1 `models/swatplus_gwflow/observations.py`

This module is central to PEST integration for streamflow.

Implemented functions:

- `make_channel_obsname(channel_id, date, site_no=None)`
- `remove_missing_observations(df, value_col="observed", missing_values=None)`
- `read_streamflow_observations_long(obs_file, date_col="date", site_prefix="site_", missing_values=None)`
- `read_channel_gage_mapping(mapping_file, site_col="site_no", channel_col="channel_id")`
- `build_streamflow_observation_table(obs_long, mapping)`
- `create_streamflow_simulation_table(obs_table, sim_long_file, sim_value_col="simulated")`
- `write_simulation_csv(sim_table, output_file)`
- `write_simulation_dat(sim_table, output_file)`
- `write_simulation_instruction_file(sim_dat, ins_file=None, obsname_col="obsname")`
- `prepare_streamflow_instruction_files(...)`
- `build_streamflow_obs_table_from_config(cfg, site_col="SITENO", channel_col="channel_id")`

### 8.2 Observation naming

Streamflow PEST observation names are generated like:

```text
cha0389_site08405400_20220101
```

or without site number:

```text
cha0389_20220101
```

This is useful for grouping by channel and parsing date from the final 8 digits.

### 8.3 Observation workflow

The streamflow observation preparation does this:

1. reads wide observed streamflow file,
2. melts to long format,
3. removes missing values,
4. reads gage-to-channel mapping,
5. merges observations with channel IDs,
6. creates unique observation names,
7. reads extracted simulated streamflow file,
8. merges by `date` and `channel_id`,
9. writes `sim_stf_day.dat`,
10. writes `sim_stf_day.dat.ins`.

### 8.4 Observation edge cases

1. Missing values default to `[-999]`, but not `-99` unless supplied. Some earlier user data used `-99`, so this should remain configurable.
2. `read_streamflow_observations_long()` requires columns beginning with `site_`.
3. `read_channel_gage_mapping()` defaults to `site_no`, but `build_streamflow_obs_table_from_config()` defaults to `SITENO`. This reflects the Pecos GIS export but can surprise users.
4. `create_streamflow_simulation_table()` uses an inner merge. Missing simulated dates or channels silently reduce the observation count. A diagnostic warning would be useful.
5. `write_simulation_instruction_file()` rewrites instruction files based on current simulation output. In a PEST++ run, regenerating `.ins` during every forward run is not ideal, because PEST control files expect a stable observation list.

For SWP, the output list can be much smaller and more stable if we use scenario summary metrics instead of every daily observed value.

## 9. Large SWAT+ output extraction

### 9.1 `models/swatplus_gwflow/outputs.py`

This module is designed for large SWAT+ text outputs.

Key functions:

- `find_swatplus_output_header_row(output_file)`
- `extract_swatplus_channel_output_long(output_file, output_csv, value_col, cha_ids, id_col="gis_id", chunksize=200_000)`
- `get_memory_usage_mb()`

### 9.2 Header detection

The header finder searches for a line whose first five tokens are:

```text
jday mon day yr unit
```

This is more robust than fixed `skiprows` for large SWAT+ outputs.

### 9.3 Output extraction

The extractor:

1. detects the header row,
2. validates required columns,
3. reads only needed columns,
4. filters selected channel IDs,
5. constructs a `date` column from `yr`, `mon`, and `day`,
6. renames the selected value column to `simulated`,
7. appends chunks to a long-format CSV.

Output format:

```csv
date,channel_id,simulated
2022-01-01,1,0.00123
```

This is highly suitable for SWP because release additions and constraint calculations are easier in long format.

### 9.4 Output-extraction edge cases

1. If no selected channel rows are ever found, the function returns an output path but may not create a file. A post-run existence check would be useful.
2. Date construction will fail for invalid year/month/day rows.
3. `cha_ids = []` means no selected channels, not “all channels.” The config comment says empty lists mean all available units, but `extract_swatplus_channel_output_long()` does not implement that behavior.
4. The function assumes the units row exists immediately after the header row, hence `skiprows=header_row + 2`.

## 10. PEST/PEST++ integration

### 10.1 `core/pest.py`

This is the main PEST integration file. It currently supports:

- base PEST control-file creation,
- observation-value updates,
- parameter-bound updates,
- basic PEST++ execution,
- reweighting,
- PESTPP-IES control-file creation and worker execution,
- PESTPP-SEN Morris control-file creation and worker execution.

Implemented functions:

```text
create_pest_control_file
update_pest_observations_from_table
update_pest_parameters_from_table
run_pestpp
reweight_pest_control_file
create_ies_control_file
run_pestpp_ies_workers
create_morris_control_file
run_pestpp_sen_workers
```

### 10.2 Base control-file creation

`create_pest_control_file()`:

1. enters `model_dir`,
2. uses `pyemu.helpers.parse_dir_for_io_files(".")`,
3. creates a Pst object from all template and instruction files,
4. sets model command and `noptmax`,
5. optionally updates observations from the streamflow observation table,
6. optionally updates parameters from active parameter database rows,
7. writes a version-2 PEST control file.

This is a good pattern for SWP if a release `.tpl` and an SWP output `.ins` file are present in `model_dir`.

### 10.3 Parameter update special handling

`update_pest_parameters_from_table()` contains thoughtful handling for SWAT+ `pctchg` parameters under log transformation. It uses a positive PEST-space parameter and a negative offset to preserve an actual model-space range like `-100` to `+100`.

This is not directly needed for SWP release amounts, because releases should usually use:

```text
partrans = none
parlbnd >= 0
parubnd = max release
```

### 10.4 PESTPP-IES support

`create_ies_control_file()` sets:

```python
pst.pestpp_options["ies_num_reals"] = ies_num_reals
pst.control_data.noptmax = noptmax
```

and sorts parameters by parameter group to avoid PEST++ warnings.

`run_pestpp_ies_workers()` wraps `pyemu.os_utils.start_workers()`.

### 10.5 PESTPP-SEN support

`create_morris_control_file()` sets:

```python
pst.pestpp_options["gsa_method"] = "morris"
pst.pestpp_options["gsa_morris_r"] = gsa_morris_r
pst.pestpp_options["gsa_morris_p"] = gsa_morris_p
```

and estimates runs as:

```python
gsa_morris_r * (pst.npar_adj + 1)
```

`run_pestpp_sen_workers()` also wraps `pyemu.os_utils.start_workers()`.

### 10.6 Missing SWP support

There is no function yet for:

```text
create_swp_control_file
run_pestpp_swp_workers
make_swp_sweep_file
rank_swp_results
```

These can be added with minimal disruption.

## 11. Current forward-run script

### 11.1 `config/forward_run.py`

The forward run is intended to live inside the copied model folder, probably as:

```text
workspace_dir/main/forward_run.py
```

It does:

1. derives `model_dir` from `Path(__file__).resolve().parent`,
2. derives config path as `model_dir.parents[1] / "config" / "setup_swatplus.yml"`,
3. loads config,
4. reads channel output config,
5. finds SWAT+ executable in the model directory,
6. runs SWAT+,
7. extracts selected channel output,
8. prepares streamflow instruction/simulation files.

### 11.2 Forward-run script edge cases

1. `setup_workspace()` currently copies binaries but does not copy `config/forward_run.py` into `workspace_dir/main`. There may be a manual workflow step not currently encoded.
2. The script references `cfg["outputs"]`, but the provided config does not include `outputs`.
3. It regenerates instruction files during the forward run, which is risky once a PEST control file is already built.
4. It assumes the config directory is exactly two levels above `main`: `model_dir.parents[1] / "config"`. This works for `project/ihydrocal_workspace/main`, but may not work for arbitrary worker layouts unless pyEMU worker copies preserve relative path expectations.
5. It does not currently apply release schedules or management scenarios.

For SWP, a separate `forward_run_swp.py` or a mode-aware `forward_run.py` is recommended.

## 14. Packaging, tests, and CI issues

### 14.1 Test results

I ran tests two ways.

From the repository root without setting `PYTHONPATH`, tests fail because `tests/test_basic.py` imports:

```python
import src.ihydrocal as ihydrocal
```

but internal package imports expect `ihydrocal`, not `src.ihydrocal`.

With `PYTHONPATH=src`, one test passes and one fails because `tests/test_basic.py` expects version `0.0.0b2`, while the package is `0.0.0b3`.

## 15. Main edge cases relevant to `pestpp-swp`

### 15.1 Missing `pestpp-swp` binary

The uploaded repo includes `pestpp-glm`, `pestpp-ies`, `pestpp-opt`, and `pestpp-sen`, but not `pestpp-swp`.

### 15.2 Missing `outputs` config section

Both `forward_run.py` and `all_workflows.py` expect `cfg["outputs"]["swatplus"]["channel"]`, but the config template does not define it.

### 15.3 `cha_ids: []` ambiguity

The config comments say empty lists mean all units, but the extractor treats an empty `cha_ids` list as no selected channels. For SWP, selected channel IDs are essential.

### 15.4 Stability of `.ins` files

Regenerating instruction files inside a PEST forward run can create unstable behavior if the observation list changes. SWP summary outputs should use a stable output file with a stable instruction file.

### 15.5 Release parameter naming

PEST names are short and often lowercase. Release parameters need a naming convention that avoids duplicates after truncation.

### 15.6 Decision variable scale

Release variables are likely in `cms`, `m3/day`, or `acre-ft/day`. The framework must be explicit about units and conversion. SWAT+ channel output `flo_out` appears to be used as streamflow/discharge, likely cms in the user’s current workflows.

### 15.7 True SWAT+ release vs post-processed release

Adding release after extracting output is simple but not fully hydrodynamically propagated through downstream channels. If downstream routing, reservoir behavior, or water quality effects matter, release must eventually be applied through real SWAT+ input-side mechanisms.

### 15.8 Parallel workers and file mutation

Each `pestpp-swp` worker must receive its own copied model directory. pyEMU workers support this, but all scenario-specific output files must be relative and local to the worker directory.

### 15.9 Windows/Linux executable naming

Existing functions sometimes default to `.exe` and sometimes not. `run_pestpp_ies_workers()` defaults to `pestpp-ies`, but `run_pestpp()` defaults to `pestpp-glm.exe`. SWP functions should support both.

## 16. Recommended SWP integration strategy

The best match to the current codebase is a staged implementation.

### Stage 1: Scenario-sweep post-processing release

Use `pestpp-swp` to sweep release variables. Each scenario:

1. writes `release_schedule.csv` from `release_schedule.tpl`,
2. runs SWAT+ normally,
3. extracts selected channel flow to `cha_flo_out_day.csv`,
4. applies release additions to selected channels/dates,
5. computes summary metrics/constraints,
6. writes a stable `swp_outputs.dat`,
7. PEST++ collects results into `sweep_out.csv`.

This stage is fast to implement and safe for the original model dataset.

### Stage 2: SWAT+ input-side release

Once Stage 1 works, modify actual SWAT+ point-source, recall, reservoir, or management files before running SWAT+. This would route release through SWAT+ and is more physically correct.

### Stage 3: Optimization

Use SWP results to identify reasonable decision-variable ranges, then migrate to:

- `pestpp-opt` for single-objective constrained optimization, or
- `pestpp-mou` for tradeoff/Pareto optimization.

---

## 17. Overall conclusion

The current iHydroCal project is ready for a first `pestpp-swp` extension, but the implementation should be careful not to overload the existing calibration workflow. Release-water scenario sweeping should be added as a **management-scenario workflow**, not as a calibration parameter workflow.

The least disruptive path is:

1. add release-specific utilities under `models/swatplus_gwflow/releases.py`,
2. add SWP control/run helpers to `core/pest.py`,
3. add SWP config blocks to `config/setup_swatplus.yml`,
4. add a separate `config/forward_run_swp.py`,
5. add an example script or notebook for the Pecos release sweep.

This preserves the existing GLM/IES/SEN calibration design while adding a new management-scenario branch that can later be upgraded to true optimization.
